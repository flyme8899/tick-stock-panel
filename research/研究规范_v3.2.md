## 一、数据来源

### 1.1 只读快照

- 研究**只读「数据快照」**
- **不连 TSP 生产数据库**
- **不在生产服务器的容器里跑研究脚本**

### 1.2 快照发布与校验

| 项 | 规则 |
| --- | --- |
| 发布地址 | `http://43.161.233.138/snapshots/` |
| 文件 | `YYYYMMDD.tar`（parquet）或 `YYYYMMDD_csv.tar`（CSV） |
| 内含 | `MANIFEST.json`（表、行数、日期范围、校验值） |
| 校验 | 下载后**先用同名 `.sha256` 校验** |
| 报告要求 | 注明**快照版本** 和 **tar 的 sha256** |

任务书会写明用哪个快照。

### 1.3 外部数据抓取

- 需要外部数据（东财、akshare、新浪、巨潮等）时，**在自己环境抓**
- **限速：并发 ≤ 3，失败重试带间隔**
- 原始数据一并存档，记录来源接口
- **严禁从 TSP 生产服务器批量请求外部接口**

### 1.4 数据源替换

如东财 403 改用新浪，**必须在报告里如实说明原因和差异**。

### 1.5 数据不足或缺口处理

**5.1 先报缺口，不先动手**

发现快照数据不够（时间太短、字段缺失、覆盖率低等），先在报告里写明：
- 缺什么表 / 字段
- 缺多长时间
- 对结论的影响
- 补全方案（数据源接口、预计条数、耗时）

**5.2 补全方式二选一**

| 方式 | 适用 | 要求 |
| --- | --- | --- |
| **a) 研究方自行抓取** | 一次性、不需入线上库 | 在自己环境抓；限速（并发≤3、失败重试带间隔）；原始数据和抓取脚本放 `research/<课题名>/data/raw/` 和 `fetch_*.py`；记录来源接口、抓取时间、条数、失败数 |
| **b) 交我方补采** | **需长期使用或进入线上库** | **不要自己写入线上**；写成「补采建议」交我方，由我方评审后在服务器补采入库，再出新快照 |

**5.3 多源校验**

补来的数据须与快照中已有重叠区间对比（抽样或全量），报告：
- 一致率
- 量纲换算（如万元→元）

**一致率低的数据源不得使用**，并说明原因。

**5.4 不能补的如实写**

如：接口不可回溯、历史已被覆盖（如业绩快报）、需付费、被 403/WAF 拦截。

写明原因，缩小研究范围或跳过该部分。

**不得用模拟或推算数据冒充真实数据**（`run_meta.json` 标注 `data_source=REAL`）。

**5.5 补全后仍不达标**

**停下报告，不硬跑。**

### 1.6 分钟数据（单独发布，不在快照内）

| 项 | 规则 |
| --- | --- |
| 清单 | 先下载 `http://43.161.233.138/minute/MANIFEST.csv` |
| 数据 | 按需下载 `/minute/kline_minute_YYYYMMDD.csv.gz` |
| **不要整库拉取** | — |

**字段**：`symbol`、`datetime`、`open`、`high`、`low`、`close`、`volume`、`amount`（A 股 1 分钟 K 线）

**口径**：
- 价格为**写入当天的前复权价**（非原始价）
- `amount` 为**原始值**
- **跨除权日须自行处理复权**

**覆盖**：
- 2025-07-25 前每天仅 29 只股票
- **全市场研究从 2025-07-25 起取样**
- ETF 和指数**无分钟数据**，需要时按 5.2 b) 提补采建议

**报告要求**：注明所用日期范围及文件 sha256。

### 1.7 账号

**下载账号与上传账号是两个不同的账号**，均由用户单独提供，**不得写进代码、报告或任务书**。

## 二、口径

### 2.1 交易成本

- 统一：**来回 18.2bp**（含每边 5bp 滑点）
- 另做**滑点敏感性（0 / 5 / 10 bp 每边）**

### 2.2 展示与时间

- **红涨绿跌**
- 日期一律**北京时间**
- 公告类事件：**公告后第一个交易日开盘买入**，杜绝未来函数
- 同一事件多次披露：**取最早公告日**

### 2.3 样本过滤（事前固定、不调参）

剔除：
- ST
- 上市不满 1 年
- 一字涨停买不进
- 日均成交额 < 5000 万

（任务书另有规定的除外）

### 2.4 基准

- **默认基准：申万一级行业等权**
- 指数基准（沪深300/中证1000 等）**只作对照**
- **凡结论只在指数基准下成立、在行业等权下不成立，一律视为风格 beta，不算 alpha**
- 条件允许时加做**规模中性化**

### 2.5 显著性

- 默认：**按买入日聚类的 t 值**（每日平均超额再做 t 检验）
- **Newey-West t 作补充**
- 多重检验：**Bonferroni**，分母为**全部测试组合数**

### 2.6 每个结论必须给（7 项）

1. 样本数
2. 交易日数
3. 时间覆盖
4. 缺失率
5. 训练/验证（按时间切分）**同号性**
6. **去掉贡献最大的 5 个交易日**后的稳健性
7. 逐年表现（**含最近 3 年单独列出**）

### 2.7 卖出规则

**必须有最长持有期上限**，不允许「不止损就一直持有」这类无上限规则。

### 2.8 数据不够就停

任务书写明的门槛不达标 → **先停下报告，不硬跑**。

## 三、产出与归档

### 3.1 课题目录结构

每课题一个目录 `research/<课题名>/`，**固定包含**：

| # | 内容 | 说明 |
| --- | --- | --- |
| 1 | `run.py` 或分步脚本 | **可一键复现，连跑两次结果一致** |
| 2 | 结果表 | csv / parquet |
| 3 | `REPORT.md` | 中文，**先写结论：可用 / 仅提醒 / 暂停**，再写依据 |
| 4 | `README` 或 `run_meta.json` | 快照版本、数据来源、成本口径、基准、检验门槛、运行环境 |
| 5 | **`data/raw/SOURCES.md`** | 逐个原始文件一行：**文件名、来源接口、抓取时间、参数、行数、sha256（64 位十六进制）、多源校验结果** |

### 3.2 禁止

- **不得把成果留在 `/tmp`、容器内或个人临时目录**
- **研究只出报告**：不改线上代码、不改线上配置、不推送通知
- 需要落地的，写成建议，由我方评审后另开 PR

### 3.3 上交（v3.2 新增）

**打包**：整个课题目录打包为 `<课题名>_<YYYYMMDD>.zip`

**上传命令**：

```bash
curl -u research_upload:<上传密码> -T <课题名>_<YYYYMMDD>.zip \
  "http://43.161.233.138/upload/<课题名>_<YYYYMMDD>.zip"
```

**返回码**：

| 码 | 含义 |
| --- | --- |
| **201** | 成功 |
| **409** | 同名已存在，**不能覆盖**，重交请换日期或加 `_v2` |
| **401** | 账号错误 |
| **413** | 超过 **2GB** 上限 |

**限制**：
- **只接受 `.zip`**，不能建子目录
- **单个文件超过 50MB 的不打包**，只在 `SOURCES.md` 登记，**原件保留至少 6 个月**
- **研究方本地目录不得删除**

**后续**：上传后 **10 分钟内**自动解压到 TSP 服务器 `research/<课题名>/`，并按 `SOURCES.md` 核对 sha256，**核对不过的退回重交**。

## 五、功能优化与策略调优类课题（v3.2 细化）

### 5.1 先固定基线

报告**第一部分**写清**现有规则的原始参数和表现**，所有改进都与基线比较。

现有代码由**我方从仓库导出**对应版本提供，**研究方不连线上**。

### 5.2 调参预算事前写死

- 任务书写明**允许调的参数**及**每个参数的取值档位**
- **组合总数即 Bonferroni 分母**
- **不得看完结果再加参数或扩大取值范围**

### 5.3 样本外三段切分

按时间切为：**训练 / 验证 / 留出**三段。

| 段 | 用途 |
| --- | --- |
| 训练 | 参数**只在此段选定** |
| 验证 | **确认** |
| **留出（最近 6 个月）** | **只在定稿时跑一次**，结果如实报告 |

### 5.4 门槛

扣成本后，改进须同时满足：
1. **三段同号**
2. 去掉贡献最大的 5 个交易日后**方向不变**
3. 相对基线超额的**日聚类 t 达到 Bonferroni 门槛**

否则**维持现状**。

### 5.5 简单优先

- 效果相当时选**参数少**的版本
- 以**参数平台**而非单点最优为准
- **相邻档位表现应接近**，孤立尖峰视为**过拟合**

### 5.6 落地

通过的写成「**参数变更建议**」，列明：
- 配置项
- 旧值
- 新值
- 预期影响
- 回滚条件

由我方评审后开 PR，**先灰度或仅提醒，观察 20 个交易日后再正式生效**。

### 5.7 不需回测的功能改进

（如补字段、改进计算口径、交互优化）按「**建议书**」提交，由我方评估排期。

## 六、功能逻辑问题（v3.2 新增）

### 6.1 研究方只发现和举证，不修

发现 TSP 输出与预期不符（指标算错、日期错位、口径不一致、信号触发与规则描述不符等），写「**问题报告**」 `ISSUE_<序号>.md` 放入课题目录，**随 zip 一起上传**。

### 6.2 问题报告必须包含

| # | 内容 |
| --- | --- |
| 1 | **现象**：哪个功能、哪个字段、哪几天哪几只股票 |
| 2 | **预期**：按规则或常识应为何值 |
| 3 | **证据**：用快照或外部数据复算的结果，**附最小复现脚本** |
| 4 | **影响**：是否影响已有研究结论 |

### 6.3 我方处理

核实后开修复 PR、上线，必要时重算历史数据并出新快照，并告知哪些旧结论需用新快照重跑。

### 6.4 影响当前课题结论的

**暂停该部分**，等修复后的快照再继续。

**不得在研究代码里自行「修正」后照常出结论**。

不影响的，在报告中注明后继续。

### 6.5 不确定是否为 bug 的

同样提交问题报告并标「**待确认**」，由我方判定是 bug、设计如此，还是规则描述不清。
